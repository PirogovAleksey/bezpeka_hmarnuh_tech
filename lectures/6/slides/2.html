Тема 6.2: Децентралізоване управління ідентифікацією

Проблеми централізованої ідентифікації

  • Єдина точка відмови (Single Point of Failure): компрометація одного IdP каскадно впливає на тисячі залежних сервісів
  • Масштабні витоки даних (Data Breaches): мільярди записів скомпрометовано через централізоване зберігання
  • Порушення приватності (Privacy): IdP має повну картину активності — які сервіси, коли, звідки
  • Залежність від постачальника (Vendor Lock-in): блокування акаунта = втрата пошти, файлів, 2FA одночасно
  • Фрагментація ідентичності (Identity Silos): пересічний користувач підтримує понад 100 окремих облікових записів
  • Відсутність контролю: провайдер може видалити або заблокувати ідентичність у будь-який момент

Традиційна ідентифікація vs SSI

Self-Sovereign Identity (SSI) — Суверенна ідентичність

  • Володіння (Ownership): користувач є єдиним власником своєї ідентичності — жоден провайдер не може її видалити
  • Контроль (Control): ви самостійно вирішуєте, яку інформацію і кому розкривати
  • Портативність (Portability): ідентичність не прив'язана до жодного конкретного провайдера чи платформи
  • Приватність (Privacy): мінімальне розкриття (Selective Disclosure) — лише необхідні атрибути
  • Довговічність (Persistence): ідентичність існує доти, доки цього бажає власник, незалежно від долі провайдера
  • Інтероперабельність (Interoperability): відкриті стандарти W3C забезпечують сумісність між різними гаманцями та мережами

Decentralized Identifiers (DIDs) — Структура

DID Document — Документ ідентифікатора

  • id: сам DID — унікальний ідентифікатор, ключ для пошуку документа в реєстрі
  • verificationMethod: набір публічних ключів для верифікації підписів та шифрування повідомлень
  • authentication: визначає, які ключі та протоколи використовуються для автентифікації власника DID
  • service: endpoint-и для взаємодії — URL для обміну Verifiable Credentials або месенджер
  • Зберігання: розподілений реєстр (блокчейн) або інше верифіковане сховище
  • Формат: JSON-LD документ з семантичним контекстом для інтероперабельності

Verifiable Credentials — Трикутник довіри

Структура Verifiable Credential

@context

Семантичний контекст для інтероперабельності

type

Тип документа (UniversityDegree, DriverLicense)

issuer

DID видавця — однозначна ідентифікація організації

credentialSubject

Дані про суб'єкта: ПІБ, ступінь, спеціальність

proof

Криптографічний підпис — гарантія автентичності та цілісності

Zero-Knowledge Proofs (ZKP) — Докази з нульовим розголошенням

Криптографічні схеми ZKP

  • BBS+ Signatures: Selective Disclosure — з одного підписаного credential показати лише вибрані поля, зберігаючи дійсність підпису
  • zk-SNARKs (Succinct Non-interactive Arguments of Knowledge): доведення довільно складних тверджень за константний час верифікації — використовує Zcash
  • zk-STARKs (Scalable Transparent Arguments of Knowledge): без довіреної ініціалізації (Trusted Setup), стійкість до квантових обчислень
  • Переваги для VCs: користувач доводить, що credential задовольняє умову, не розкриваючи сам credential
  • Практичне застосування: вхід до клубу (вік >= 18), KYC без копій документів, анонімне голосування

EU Digital Identity Wallet — eIDAS 2.0

Microsoft ION — Identity Overlay Network

  • Архітектура: DID мережа побудована як Layer 2 рішення поверх блокчейну Bitcoin
  • Протокол Sidetree: пакетна обробка тисяч DID-операцій (створення, оновлення, деактивація) в одній BTC транзакції
  • Масштабованість (Scalability): забезпечує масштабованість при збереженні безпеки базового блокчейну
  • Інтеграція з Azure AD (Microsoft Entra ID): корпоративні клієнти поступово впроваджують децентралізовану ідентифікацію
  • Відкритий код (Open Source): розвивається спільнотою Decentralized Identity Foundation (DIF)
  • Практичне значення: міст між традиційною корпоративною інфраструктурою та децентралізованим майбутнім
